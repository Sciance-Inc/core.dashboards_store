# How is the Store organized?

::alert{type="info"}
The Store uses a three-tier architecture to separate data access from reusable transformations and dashboard-specific serving tables.
::

![Store architecture](/using/architecture.webp "architecture")

## The three layers

### The interfaces layer
Interfaces map external databases, such as GPI, GRHPAIE, and Bi_distribution, to the core_dashboards_store.

* When used in the `Core.dashboards_store`, interfaces are almost always used to select and rename columns.
* You can use interfaces in your `cssXX.dashboards_store` to:
  * Union data from multiple databases
  * Materialize data from an external server

There should never be any business logic in the interfaces layer. If you need to do some complex data transformation, you should do it in the marts layer.

### The marts layer
The bread-and-nutella of the core_dashboards_store.

Marts gather reusable facts and dimensions. The store ships with two marts: **education services** and **human resources**. More marts will be added in the future.
Mart tables are built from the interfaces by cleaning, transforming, and combining them. They can also use tables from the same mart or from another mart. They contain data and indicators that can be used as building blocks for dashboards.

Usually, a mart table is used by multiple dashboards.

#### Seeds, adapters and business rules

::alert{type="info"}
Seeds and adapters are configuration-hooks and must be populated in order for the store to work.
::

Not all the information we need can be pulled from the interfaces. Sometimes we need business rules to be fed into the core_dashboards_store. To do so, the store relies on two mechanisms: **seeds** and **adapters**.

* **seeds**: seeds are **arbitrary data** injected into the marts. A seed is a `csv` file uploaded into the database before the ETL run. A lot of configuration is done through seeds. For example, the `human_resources` mart uses a seed to determine which employment codes should be considered `active`. As this is a school board decision, the `core` cannot provide this information by using only the database. You have to provide it to the store so it can be used in the ETL. Seeds are mainly used for filtering and remapping.
* **adapters**: adapters are **arbitrary SQL code** injected into the marts. Sometimes a seed is not flexible enough to handle a school board-specific business rule and you need to write SQL code to do the job. For example, the `educ_serv` mart uses adapters to determine which students are enrolled in adapted programs. As the business rule can vary greatly from one school board to another, it is not possible to provide a generic solution based on a predetermined subset of columns.

### The reporting layer

The reporting layer is where the tables used by the dashboards are built.

The reporting layer contains the tables the dashboards connect to. These tables are intentionally shaped as dashboard-serving tables, often as one-big-table or pre-aggregated outputs that simplify Power BI models. They are built from the marts, but they can also use tables from the same reporting layer or from another reporting layer.

The difference between the marts layer and the reporting layer is semantic rather than technical: if a table or business definition is used by multiple dashboards, it should probably be promoted to a mart. If it is only used by one dashboard, it belongs in the reporting layer.
